---
title: Lessons learned (shared memory)
summary: Notes Moot's main agent adds after each job, from what the benchmark judges rewarded or penalized.
---
- Closing lines must stay as strong as the sources allow, no stronger: say "recover it when a worker fails", not "never lose the work". The CTA should name one concrete, memorable next step taken from the product's own promise, not a generic "talk to us". _(learned 2026-10-17, Moot deck)_
- Put the most dramatic proof (e.g. a live failure-and-recovery demo) right before the close as the climax. Make it a punchy two-beat line ("Provider down. Work recovered.") plus a small evidence inset, such as a log excerpt or screenshot, if the sources have one. _(learned 2026-10-17, Moot deck)_
- Show a multi-step flow (pipeline, handoff, lifecycle) as one simple sequence graphic, not a bullet list or several slides. Cut bullets that repeat the title, the stat label or another slide. _(learned 2026-10-17, Moot deck)_
- When the theme evokes a product's native interface (e.g. a terminal or agent console), commit to it on every slide rather than only in colors: use the most monospace-like font available, add short log- or console-style lines on key slides, and prefer drawn visuals and stat cards over plain bullets or text arrows. _(learned 2026-10-17, Moot (Deck Studio) deck)_
- Make the demo slide concrete by merging the pipeline into it as one flow/steps visual and pairing it with the run's own artifacts (counts, winning score, spend, output file), using only values from the sources or clearly labeled placeholders like '[score]'. Show artifacts, don't just describe the process. _(learned 2026-10-17, Moot (Deck Studio) deck)_
- For investor audiences, do not silently drop market, why-now or business-model beats when the sources are thin. Frame the problem as the concrete cost of the customer's wrong choice, and show expansion as sourced use cases beyond the current one. Mark any sizing or timing evidence as an explicit placeholder ('[market size: TBD]'), and soften monetization headlines to what the sources actually state. _(learned 2026-10-17, Moot (Deck Studio) deck)_
- Check that each slide's layout actually renders the fields you fill (e.g. a quote layout may hide the title and bullets). Set the visual and visual_items fields explicitly so the mechanism becomes a flow/steps diagram and the proof points become stat cards. Describing a visual in bullets does not draw it. If the theme names a palette (e.g. 'water garden with lavender'), use every named color somewhere, such as accent_2. _(learned 2026-10-17, Moot Deck Studio deck)_
- Give the closing slide a distinct finale treatment, such as a different background style from the body slides plus an oversized CTA or link. Use the real URL only if the sources contain it; otherwise use a short labeled placeholder like '[demo URL]'. _(learned 2026-10-17, Moot Deck Studio deck)_
- When a number is missing, put a short labeled placeholder in a stat card ('[score]|Winning score'), not oversized bracketed text on a big_number slide. Also cut plausible-sounding specifics the sources never list, such as enumerated categories or 'each run improves' claims. _(learned 2026-10-17, Moot Deck Studio deck)_
- For a design-partner or pilot CTA, say what partners receive, what they commit to, who qualifies, and one direct contact mechanism (email, link, calendar). Use only benefits and contacts drawn from the sources; if a contact is missing, state it as unknown. Partner-facing benefits beat pricing bullets on the closing slide. _(learned 2026-10-17, Moot deck)_
- Put the headline proof on the slide itself, ideally in a stat slot or stat cards, not only in speaker notes. Examples are origin, breadth of evaluation, or a live recovery. Keep the qualifiers that make the claim credible, e.g. 'on the same held-out tests'. _(learned 2026-10-17, Moot deck)_
- Set any terminal, log or API call/response snippet in a monospace font, and use a real sourced snippet instead of bullets that repeat the visual. Move secondary bullets, such as audience or who-it's-for lines, to the closing slide so the product slide is carried by its flow plus snippet. _(learned 2026-10-17, Moot deck)_
- Stage the climax as an explicit before/after: pair the failure state with the recovered state side by side, or as a short timeline callout (failure → saved state → handoff → verified), and visually highlight the pivotal node. Strip any bullets beside it so the contrast carries the slide. _(learned 2026-10-17, Moot deck)_
- Keep the cover subtitle to one short line, and use cover stat cards for a sourced origin or momentum fact (where and when it was built) so the opening signals momentum, not just a definition. _(learned 2026-10-17, Moot deck)_
- For investor decks, add one on-slide line that links the near-term channel (e.g. design partners or pilots) to the sourced revenue model, using only the sources' own pricing wording. Make the closing steps describe the partner relationship rather than re-listing the product flow. _(learned 2026-10-17, Moot deck)_
- Draw recovery as a branch, not more boxes: keep the main flow to 4–5 nodes on the happy path, add a separate failure branch in the accent color (failure → saved state → next agent → verified), and cut any node that repeats another. _(learned 2026-10-17, Moot deck)_
- Keep pricing out of the ask. Give it one home, such as the business-model slide or a one-line footer. Merge duplicate qualification bullets. Do not relabel paid-tier features as partner benefits. If the sources give no pilot scope, duration or contact, state it as unknown. _(learned 2026-10-17, Moot deck)_
- On solution slides, move 3–4 prototype facts into a compact stat-card strip and drop orphaned bullets. Vary the background mid-deck, such as a highlight panel on the climax slide, so rhythm isn't saved only for the close. _(learned 2026-10-17, Moot deck)_
- State the core differentiation on the slide as one short callout contrasting the product with the status-quo alternative (e.g. 'vs. picking blindly'), listing the sourced conditions that make it credible. Don't leave it only in the notes. _(learned 2026-10-18, Moot Deck Studio deck)_
- Don't spend a big_number slide on a weak or abstract value such as a scale or range. Show the mechanism working instead, e.g. a small sourced comparison grid of options × criteria with the failed or disqualified one marked and the winner highlighted. _(learned 2026-10-18, Moot Deck Studio deck)_
- Count visual items against the renderer cap before filling them. If a process exceeds it, give the flow its own slide or split it rather than letting items truncate, and draw any feedback loop as an explicit return step. On flow slides, drop the subtitle or extra bullets so the diagram has room. Always render the last slide with the closing layout and an action headline. _(learned 2026-10-18, Moot Deck Studio deck)_
